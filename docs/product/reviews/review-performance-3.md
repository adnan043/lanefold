# Performance review 3 (read-only, new findings only)

Date 2026-11-03. Scope: `src/server/*.ts`, `src/server/routes/*.ts`, `src/server/jobs/*.ts` against `prisma/schema.prisma` and the migrations. No code changed, nothing run.

Already fixed since `review-performance.md` / `review-query-plans.md` (not repeated): `/boards/:id/rev` is one query (`boardAccess` returns `rev`), `unread-count` is one capped query, board open uses the per-lane `UNION ALL`, lane paging uses `cardsAfter` (row comparison), the move route takes the lock after the pre-checks, indexes `notifications(user_id, workspace_id, id desc)`, `cards(board_id, id desc) WHERE archived_at IS NOT NULL` and the trigram GIN indexes exist as migrations. N+1: none found; no `skip:` / offset paging; no per-request `count()` on a hot path; the only `cache.getOrSet` use (`entitlements.ts:127`) is correct (1 h TTL, cleared by `invalidateAppSettings`, nothing personal).

## Findings, most impactful first

1. **Chat send is about 10 sequential round trips** (`src/server/routes/chat.ts:770-865`, plus `requireConversation` at 172-187). Chain: `conversationAccess` (+ `getEntitlements`), replay `find()`, the rate-limit pair, the optional parent read, `mentionable` + `cardsInWorkspace`, `mentionedInBody` (`namesOf`, a separate read after `mentionable`), then the transaction (`conversation.update`, `message.create` with nested creates, optional reply update, `markRead`, optional notification insert), then `shapeMessages` (reactions, users, refs). Over the ~5 round-trip budget, and the `conversation.update` row lock is held while the rest of the tx runs. Fix: (a) run the replay `find()`, the two rate-limit reads and the parent check in one `Promise.all`; (b) fetch names inside `mentionable` (same `Promise.all`) and pass them to `mentionIdsIn`, removing `mentionedInBody`'s extra trip; (c) for the sender's own new message build the response from `created` plus the known mention ids instead of calling `shapeMessages` (a fresh message has no reactions); (d) collapse the two rate-limit reads (792-793) into one `$queryRaw` with `count(*) FILTER (WHERE created_at > now() - interval '1 minute')` over a `LIMIT SEND_PER_HOUR+1` subquery.

2. **`/chat/pulse` is two sequential queries on a 5-20 per minute poll** (`src/server/routes/chat.ts:543-558`; the section comment says "one query"). The second read only checks that the user is still in a live workspace. Fix: put that check in the first read and drop the second:
   `where: {userId: me, conversation: {workspace: {archivedAt: null, members: {some: {userId: me}}}}}` (served by `workspace_members` PK / `(user_id, workspace_id)`), then delete lines 551-556 and the `live` filter. Halves the dominant background load.

3. **Notifications list and unread count scan unbounded invisible rows** (`src/server/routes/notifications.ts:131-139` and `:195-203`, `visibleSql` at 85-100). `LIMIT` applies after the per-row `EXISTS` visibility filter. A user who lost access to a private board or chat keeps unread rows that never pass the filter, so the count (and every list page that has to skip them) walks all their unread/recent rows and runs 2-4 `EXISTS` subqueries per row. Today the walk is capped only by their history. Fix: when access is removed (board member removal, conversation leave, workspace removal), delete or mark read their notifications for that board/conversation in the same write (one `deleteMany` by `userId + boardId` / `conversationId`; `boardId` has no index on `notifications`, so scope by `(userId, boardId)` which the `(user_id, ...)` indexes serve), and as a backstop wrap the inner scan in a `LIMIT 500` subquery before applying `visibleSql` in the count.

4. **Export rate-limit read can scan an admin's whole audit trail** (`src/server/routes/import-export.ts:397-402`). `audit_events` has `(actor_user_id, id)`; filtering by `action` and `created_at` walks every event of that actor newest-first until 20 match. For a busy owner or an automation account this is O(their audit history) per export click. Fix: add `@@index([actorUserId, action, id(sort: Desc)])` to `AuditEvent` (migration `CREATE INDEX audit_events_actor_user_id_action_id_idx ON audit_events (actor_user_id, action, id DESC)`), keeping the existing query.

5. **Search rate limit is three cache round trips per keystroke** (`src/server/soft-limit.ts:15-30`, used at `routes/search.ts:35`). `softLimited` = `get` (softCount) then `softHit` = another `get` + `set`. Each is a platform call. Fix: in `softLimited` read once and write once (`const used = (await cache.get(k)) ?? 0; if (used >= max) return true; await cache.set(k, used + 1, ttl)`), or fire the `set` without awaiting it via `c.executionCtx.waitUntil`. Also make sure the web client debounces `/search` (not verified here).

6. **Export runs up to ~350 sequential queries in one request** (`src/server/routes/import-export.ts:207-300`): one card read per lane (up to 50 lanes, empty lanes included) plus 6 queries per 100-card batch, up to 5000 cards. Bounded and streamed, so it is not a leak, but it is a long single Worker request. Fix: one keyset read over the whole board ordered by `(lane position, position, id)` (join `lanes`) in batches of 100, so empty lanes cost 0 trips and batches are not split by lane; or lower `EXPORT_CARD_CAP` until it is moved to a background job (`background-jobs.md`) that writes a file.

7. **`sweepPlans` does about 4 writes per row inside the loop** (`src/server/jobs/sweeps.ts:44-48`: `updateMany`, `startGraceForOverLimit` (2 statements), `audit`). It is a daily background job paged by `PAGE_SIZE`, so acceptable, but a mass plan lapse makes a long run. Fix (only if volumes grow): downgrade the whole page with one `UPDATE ... WHERE id IN (...) AND plan = ... RETURNING id` and one `createMany` audit insert.

The duplicate `if (!board)` at ~801 is dead.
